# OpenT5 0.3.0

Edit a PS3 map zone's placed objects in the 3D view and save the result to new files. This
release builds the in-place map editor on top of the 0.2.0 toolchain: the converter, the
edit layer, and the textured 3D viewer (which draws models and worlds with their own
textures and lighting, static models on by default) carry over unchanged.

## In-place map editor

Open a zone, pick an object in the 3D view, change it, and save. The editor works on the
zone's placed objects, not its world geometry or baked lighting.

- **Object kinds:** static-model props, spawn points, objective entities and placed lights.
- **Operations:** select, move, rotate, add (from the zone's own models and the entity
  classes a gametype needs), delete and duplicate.
- **Undo and redo** across every edit, with a drag coalesced into one undo entry.
- **Property panel:** exact origin, angles and per-kind keys; typing a value is the same
  edit as a gizmo drag.

## Verify on save, and never over stock

- Saving runs the 0.2.0 checks (reparse-exact and the emulated-loader checks) plus the
  gametype entity rules. A save that fails a check, or that would break a gametype that
  worked before the edits, writes nothing and reports the failing check.
- Output always goes to a new file (`<name>.edited.ff` by default). The source zone and any
  stock zone or pak are never written.

## Real prop collision on add, move and delete

A moved or added prop stays solid, and the old spot is left clear. This was the main risk
for the release and is settled on device.

- Prop collision is axis-aligned clip cbrushes compiled into the clipMap BSP, the one
  mechanism our own builds have shown solid on PS3. The device test moving the Nuketown
  school bus confirmed it: the bus is solid at the new position and walk-through at the old
  one.
- The device test also ruled out the lighter route (editing only the prop's
  `cStaticModel_s`): collision does not follow it, so moving a prop by its render record
  alone leaves an invisible wall where the prop used to be.
- An added clip is appended to the brushVerts pool contiguously, matching retail's
  running-count layout, and is attached to the exact BSP leaf a trace reaches, so the engine
  finds it. Moving or deleting a prop moves or removes the cluster of clip brushes that sits
  in its footprint, which covers stock props as well as editor-added ones.

## Also in this release

- **Interactive viewport editing:** a translate and rotate gizmo with axis-constrained drag
  in the 3D view. Drag a prop to move it, rotate it about its up axis, and add a crate with a
  keystroke; each drives the same clip-aware edit, so render and collision stay together. The
  editing maths are covered by tests; the gizmo feel on a real GPU is the one human check in
  the end-to-end device test.
- **Path-link regeneration on save (edit-relative):** on save, links whose line of sight now
  crosses an edited clip volume are re-tested against the edited collision and dropped if
  blocked, so a moved or added prop cannot leave a path link running through it. The save is
  refused only when an edit newly disconnects a region that was connected before; a map that
  was already fragmented is reported as a warning, not a failure. The map's other links are
  left untouched. (A whole-map line-of-sight gate was deliberately avoided: retail path graphs
  read as several components under a strict line-of-sight model yet load fine, so the engine's
  path connectivity is looser than ours - see docs/research/pathlink-los-recipe.md.)
- **The signal-orange brand, startup splash and busy overlay:** the application's visual
  identity, the launch splash, and a clear busy overlay during a save or a long task.

## Device-test discipline

Device builds are staged through a fixed protocol, because a stale disc cache can serve an
old map and look like a code failure:

- Close RPCS3 and clear (or rename) the BLES01031 FIOS disc cache before copying a build;
  RPCS3 keeps a decrypted copy of the disc and will serve it if the new file is not newer.
- Copy the build, then set its modified time to now, because a plain copy keeps the old
  time and never invalidates the cache.
- Include a visible in-map marker so a stale load is obvious at a glance.
- `tools/verify_staged_map.py` confirms a staged `.ff` is the intended map before it ships.

## Known limitations

- **Baked lightmap shadows stay put.** Lighting is baked by the PC tools (cod2rad), and the
  editor does not relight. Moving or deleting a prop leaves its baked shadow (a dark patch on
  the ground) at the old position, and any baked light contribution with it. The editor warns
  when you move or delete a prop so this is expected, not a surprise. Proper relighting is a
  later item.
- **Non-axial rotation uses an axis-aligned clip.** A prop's collision clip is an
  axis-aligned box sized to its footprint, so a prop rotated off the world axes keeps a clip
  that does not turn with it. The prop renders rotated; its solid volume stays axis-aligned.
- **Sun and fog editing are not in 0.3.0.** The sun is static zone data that drives only the
  real-time sun on dynamic entities; it does not relight the baked world, so a changed sun
  reads as broken (a lit world under a sun from the wrong side). Fog is script-driven (a map
  sets it from GSC, e.g. `scr_fog_*` dvars and `setVolFog`), not a gfx_world field, so it is
  out of scope for a geometry and lighting editor. Both are left out and the editor does not
  surface a control for them; they are candidates for a later release once relighting exists.
- **Edited zones keep the original console signature**, which no longer matches after an
  edit, so editor output loads only on a client with the signature check patched out, as in
  0.2.0.
