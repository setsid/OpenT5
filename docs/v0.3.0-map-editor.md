# v0.3.0 plan: in-place map editor

Status: plan for review, no code yet.

Edit a PS3 map zone's placed objects in the 3D view and save to new files. The target is to
move, rotate, add, delete and duplicate static-model props, spawns, objectives and lights;
edit the sun and fog; undo and redo; verify on save; and never write over a stock file. Moved
or added props keep real collision, and the path-node links are rebuilt with a line-of-sight
test against the edited layout.

This builds on v0.2.0: the converter (parse, write, splice, verify, path-link baking), the
textured 3D viewer with its camera and picking maths, and the edit layer already used for
field and texture edits.

## 1. Scope

In scope for v0.3.0:

- Select an object in the 3D view (ray-pick), show its properties.
- Move and rotate with a gizmo; type exact values in a panel.
- Add (from a palette of the zone's own models / entity classes), delete, duplicate.
- Object kinds: static-model props, spawn points, objective entities, lights.
- Sun editing (direction, colour, intensity) and fog editing.
- Undo and redo across every edit.
- Verify on save (the v0.2.0 checks) and refuse to save a zone that does not verify.
- Save to new files only; stock zones and paks are never written.
- Real static-model collision for moved/added props (section 5).
- Path-node links rebuilt with a line-of-sight test against the edited collision (section 6).

Out of scope for v0.3.0 (named so the boundary is clear): editing world brush geometry,
lightmaps or the light grid (lighting stays baked; moving a prop does not re-bake its
lightmap); adding brand-new models or images that the zone does not already carry; terrain
sculpting; multi-zone edits.

## 2. Architecture

### 2.1 Edit model

An `EditSession` wraps one parsed zone (the v0.2.0 `XFile`) and holds an ordered list of
`Edit` objects. An `Edit` is a small, reversible operation with `apply(zone)` and
`revert(zone)`, so undo/redo is a cursor over the list. Edits never mutate the on-disk file;
they mutate the in-memory parsed nodes, and the file is produced only on save by the existing
`write`/splice path.

Edit kinds: `MoveObject`, `RotateObject`, `SetProperty`, `AddObject`, `DeleteObject`,
`DuplicateObject`, `SetSun`, `SetFog`. Each stores the object's stable id and the before/after
values, so revert is exact. A coalescing rule merges a drag (many `MoveObject` steps) into one
undo entry.

### 2.2 Object identity

Objects need stable ids that survive edits:

- Entities (spawns, objectives, lights that are entities): index into the parsed entity list,
  re-keyed to a synthetic id so inserts/deletes do not renumber live selections.
- Static models: index into the GfxWorld static-model draw-instance array, paired with the
  clipMap static-model entry and (when present) the entity that placed it.

A selection is `(kind, id)`. The 3D view maps a pick to a selection and back to a highlight.

### 2.3 Where each object lives in the zone

| Object | Rendered from | Collision from | Edited in |
|---|---|---|---|
| Static-model prop | GfxWorld smodel draw inst + inst | clipMap (section 5) | both, in step |
| Spawn / objective | map_ents entity string | n/a (triggers are brush models, not moved in v0.3.0) | entity string |
| Light (placed) | map_ents entity + GfxWorld light / light grid | n/a | entity + GfxWorld light array |
| Sun | GfxWorld sun GfxLight + worldspawn keys | n/a | GfxWorld + entity string |
| Fog | worldspawn / dvar / the fog asset the map uses | n/a | the fog source |

A move or rotate of a static model must update the GfxWorld draw instance (origin, the CMP
axis rows, cull bounds) AND the clipMap collision together, or the prop renders in one place
and blocks in another.

## 3. The 3D view

Extends `gui/views/mesh.py` from v0.2.0 (camera, picking, framing already exist):

- **Select:** left click ray-casts against drawn static models and against entity icons
  (billboarded markers for spawns, objectives, lights, the sun). Nearest hit wins.
- **Gizmo:** a translate/rotate gizmo at the selection; drag an axis to move or rotate, with
  snapping (grid and angle) toggleable. The pure maths (ray vs plane, axis projection) extend
  the v0.2.0 camera maths and are unit-tested without a GPU.
- **Add:** a palette lists the models the zone already carries and the entity classes the
  gametypes need; placing drops the object at a picked point on a surface.
- **Delete / duplicate:** keys and context actions; duplicate offsets a copy.
- **Property panel:** exact origin, angles, scale, and per-kind fields; editing a field is the
  same `Edit` as a gizmo drag.
- **Overlays:** the controls hint from v0.2.0, plus a selection readout and an edited-since-save
  marker.

The headless/wireframe fallback keeps working; editing maths are testable without OpenGL, and
the interactive gizmo is the one part that needs a human check on a real GPU.

## 4. Entity, light, sun and fog editing (lower risk, first)

Entities are the map_ents entity string (text), already parsed and written in v0.2.0. Moving a
spawn or objective is a key edit in that text; add/delete/duplicate are line edits; verify
re-runs the gametype entity rules so a delete that breaks a mode is caught on save. Placed
lights are an entity plus a GfxWorld light-array entry; the sun is the GfxWorld sun GfxLight
plus worldspawn keys; fog is the map's fog source. These are done first because they do not
touch the clipMap, and they exercise the whole edit/undo/verify/save loop on safe data.

## 5. Static-model collision (the key risk)

Moving or adding a prop must keep it solid. In v0.2.0 the box props were made solid with clip
brushes compiled by cod2map; the editor cannot run cod2map, so it must register the collision
itself, and the v0.2.0 work showed that a clipMap static-model-list entry alone did not give
collision on PS3. So the first task of this phase is a **spike** to settle, from stock PS3
maps whose misc_model props are solid, exactly how their collision is stored:

- Is it per-model collision reached through the clipMap static-model list plus a collision LOD
  and the collision aabb tree / leaf references?
- Or clip cbrushes the compiler baked into the clipMap at each prop?
- What does moving a prop therefore require: updating a static-model collision bound and the
  spatial tree, or inserting/moving cbrushes?

The spike reads a stock map both ways (our parser and the emulated loader) and writes the
findings to docs/research/ before any editor code touches the clipMap. The editor then
implements the confirmed representation: on a move, update the prop's collision origin/bounds
and the clipMap spatial structures that index it (so a trace still hits it); on add, insert a
collision record and re-index; on delete, remove it. Every change keeps the clipMap self
consistent, checked by the emulated loader on save.

This is the hardest part and the main schedule risk; it is sequenced after section 4 so the
editor is already useful if the spike needs more time.

## 6. Path links with line of sight

v0.2.0 bakes path-node links by distance as a single connected component (convert/pathlinks.py).
v0.3.0 adds the line-of-sight test the earlier work deferred: a candidate link is kept only when
the segment between the two nodes is clear of the edited collision (the clipMap solids from
section 5), so links no longer graze props. Links are rebuilt on save whenever the layout
changed, still widening until the graph is one connected component and failing the save if it
cannot connect. The connectivity check from v0.2.0 is reused.

## 7. Save pipeline

On save: apply all edits to the in-memory zone, rebuild path links (section 6), run verify (the
v0.2.0 reparse-exact and emulated-loader checks) and the gametype entity rules, and only then
write. Output goes to a new file chosen by the user (or `<name>.edited.ff`); the source and any
stock file are never written. A save that fails verify is reported with the failing check and
nothing is written, matching the converter's refuse-to-write rule.

## 8. Milestones

1. Edit model, undo/redo, selection and the property panel, on entities only (section 4). Save
   to new files with verify. Gizmo translate/rotate for entities.
2. Sun and fog editing.
3. Static-model collision spike (section 5) and its write-up.
4. Static-model move/rotate/add/delete/duplicate with collision kept in step.
5. Line-of-sight path links on save (section 6).
6. Polish: snapping, multi-select, the palette, overlays.

## 9. Testing

- Pure editing maths (gizmo ray/plane, transform compose, duplicate offset) unit-tested without
  a GPU, as the camera maths are.
- Each `Edit` round-trips: apply then revert leaves the zone byte-identical.
- A save round-trips: the edited zone reparses exactly and passes the emulated loader.
- The gametype entity rules catch a delete that breaks a mode.
- Device checks (the human part): the gizmo feel on a real GPU, and that a moved or added prop
  is solid in game and that path links behave.

## 10. Open questions for review

- Static-model collision representation (section 5) is unconfirmed until the spike; it sets how
  much of section 5 and the schedule is realistic.
- Fog's source varies by map (worldspawn, a dvar, or a fog asset); the editor needs the one the
  target map uses, to be settled per map during section 2.
- Default output naming (`<name>.edited.ff`) and whether to also offer "convert to its own map"
  on save.
